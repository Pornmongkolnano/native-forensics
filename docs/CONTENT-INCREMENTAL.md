# Incremental derived content updates

Update Index creates a new case content generation while permitting individual indexed documents from the previous generation to be retained. Rebuild Index continues to extract and decode every eligible document. Update is an explicit operation: reopening a saved generation remains historical and does not trigger verification or certify source freshness.

Before any reuse, the previous snapshot must pass its bounded schema, collection, coverage, locator and derived-text digest validation and belong to the same case. The current listing set is admitted under the existing aggregate listing budgets. Ordered source containers are then fully rehashed against their recorded SHA-256 values. The same verification runs after processing, including an update that reuses every indexed document. No inode, timestamp or file-size shortcut replaces either full-byte check.

Production reuse requires the same freshly inspected complete `DocumentDecoderIdentity` at both boundaries and equality with the previous generation: worker/broker executable hashes and signing CDHashes, decoder contract/version, isolation backend, typed decode options/options SHA-256 and the current XPC protocol version. Every indexed document must retain the exact matching `DocumentDecodeProvenance`; its derived digest agrees with the existing page/label/kind/truncation digest recipe. Equal worker bytes alone cannot certify unchanged broker or options. Historical nil identity/provenance forces production decoding; the explicitly unknown legacy injected-test branch retains nil fields and cannot accept a schema-2 proof without a full identity provider.

Reuse also requires identical complete index limits and `ContentIndexSource` binding. That binding covers the selected container hash/size, ordered container hashes, recorded engine version/patch/options, volumes and complete listing digest. A reused document must have the exact current evidence ID, file entry and canonical locator. Any indexed-file binding inconsistent with an otherwise unchanged source is rejected as an invalid prior snapshot. Changed source bindings rebuild all eligible documents from that source; unchanged evidence elsewhere in the case can still reuse its indexed documents.

Only validated indexed documents are reused. Unsupported, failed and no-text files are retried through the decoder; pending statuses and file/input/text budget decisions are recomputed in current case/listing order. Reused files consume the same input-byte and retained-text accounting as a full rebuild, so reuse cannot bypass coverage budgets. Files beyond the work limit remain explicitly omitted/pending, and directories/uncovered listings retain the same counts. Partial derived text stays partial when reused. Changing any index limit disables reuse for that update.

The update publishes a fresh generation ID. References and query hits from the previous generation cannot resolve in the new one. The existing compare-and-save, cancellation/deadline drain and atomic publication rules still apply; an unsuccessful update before publication leaves the previous saved generation intact. A decoder or source change at either verification boundary rejects the update rather than publishing a mixture of old and changed inputs.

Progress distinguishes processed files, reused indexed files and rebuilt files. Rebuilt counts actual preview/extraction/decoder attempts, including attempts producing skipped/failed/pending text-budget records. File-byte/input-budget exclusions are processed records but do not count as decoder attempts. These counters describe performed work and are not a claim about process RSS or speedup.

This is reuse of a locally validated derived generation, not a cryptographic signature of examiner-authored cache bytes. The existing index digests detect inconsistent/corrupt derived data; they do not independently prove that an adversarially rewritten and consistently rehashed cache was produced by a trusted decoder. Source-container verification, extracted-content receipts, derived-text digests and historical provenance remain distinct claims.

The content workbench receives the same injected application scheduler as its parent window, defaulting to the shared scheduler. One content-index permit covers historical index/listing reads and binding checks, or the complete rebuild/update with both fresh source checks and atomic cache publication. Queued cancellation starts no index worker. Cancellable workers are awaited through their drain; once the atomic publisher has begun, it runs to completion and retains the slot through cleanup even after cancellation or window close. A late cancel presents the committed generation when the same case remains open. Closing a window clears presentation but keeps its active owner until publication and permit release finish. Matching saved query text and presenting existing references use no heavy-work admission; freshly reopening recovered content uses its document-preview owner.

The incremental regression suite uses synthetic fixed payloads, preview/verification counters and real temporary source files to exercise unchanged reuse, changed-source isolation, decoder/engine/options/limit invalidation, exact file binding rejection, partial/budget behavior, both full-hash boundaries and cancellation/deadline drain. `ContentIndexDecoderBindingTests` independently compares the old DTO encoding, reopens retained partial/current proofs, verifies real source SHA at both boundaries, changes broker/signing/options/backend while keeping worker SHA equal, rejects closing-fence changes and receipt mismatches, and rejects persisted/reference tampering without rewriting it. Decoder metadata in these tests is injected synthetic metadata; it is not an actual XPC/signing runtime receipt. Store tests additionally share one scheduler between two workbenches to cover queued load/update cancellation, publisher ownership during late cancellation and close, and unchanged hashes with a new generation after reuse. Test source alone is not execution evidence; current serial repository gates must confirm the implementation and native workbench separately.
