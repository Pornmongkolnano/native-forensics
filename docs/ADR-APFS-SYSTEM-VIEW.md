# ADR: Source-bound APFS views through the macOS disk-image driver

Status: experimental implementation; the exact combination matrix governs advertised support.

The existing audited TSK engine remains the filesystem engine for its validated formats. APFS is a separate adapter rather than an unreviewed extension to the TSK protocol. This adapter uses Apple's system disk-image/APFS driver to read **allocated regular-file main forks in one selected current APFS volume or an explicitly selected validated plaintext snapshot**. It does not interpret APFS block structures itself or claim deleted-file recovery, APFS encryption cracking, boot FileVault unlock, or unvalidated encrypted historical combinations.

[Apple's current APFS overview](https://developer.apple.com/documentation/foundation/about-apple-file-system) recommends filesystem APIs for normal file access and distinguishes the on-disk APFS reference for direct readers. [Apple's disk-image guide](https://support.apple.com/guide/disk-utility/create-a-disk-image-dskutl11888/mac) describes encrypted disk images as a separate operation from protecting the system disk with FileVault. The local `hdiutil(1)`, `diskutil(8)` and `mount_apfs(8)` manuals are executable-version-specific primary references for the command contract.

## Decision and ownership

The adapter first opens the selected regular image using an anchored, no-follow descriptor and verifies the exact selected-file SHA-256 receipt. It creates a unique private image using `fclonefileat` from that descriptor, or a bounded streaming copy when cloning is unavailable. A clone is a private copy-on-write object, not an in-place source mutation or a hard link. Its complete hash must independently equal the selected-container receipt before mounting. The original source and private image are hashed again after the operation. A changed path/identity/hash prevents successful result publication.

Only the unique private image is attached. `hdiutil attach -readonly -noautofsck -noverify -nobrowse -noautoopen -nomount -plist -stdinpass` is used for compatibility with the declared macOS deployment target. macOS 27 deprecates parts of `hdiutil` in favor of `diskutil image`; this adapter cannot assume that replacement exists on every advertised OS. Independent complete hashes replace the DiskImages checksum cache: `-noverify` prevents its observed checksum-xattr/ctime change on encrypted private UDRO files. The driver must report bounded, uniquely identified APFS volume candidates. After recognizing the encryption state and, when required, explicitly unlocking the supported Disk crypto user through stdin without mounting, `diskutil mount readOnly nobrowse -mountOptions noexec,nosuid,nodev -mountPoint ...` mounts only that volume. The kernel descriptor must actually have filesystem type `apfs` plus read-only/no-exec/no-suid/no-device flags. The known device, filesystem identity and pinned root must remain the same throughout traversal. No filesystem repair, shadow file, remount as writable, or source-destination overlap is permitted.

Traversal is descriptor-relative, bounded and does not follow symlinks, enter another mounted filesystem, or execute file contents. Regular-file bytes are hashed using a held descriptor before accepting them. Large files, depth/row limits and unreadable entries are explicit partial coverage. A later verified read remounts a fresh source-bound private copy and checks the complete file digest against the recorded entry, rather than trusting inode/mtime alone. Mounted inode/relative-path references are logical identifiers, never claims that offsets in an encrypted or compressed disk-image container correspond to plaintext file bytes.

The original nil-UUID default still requires exactly one identified APFS volume. The explicit selector uses a stable UUID, rejects duplicate/absent/ambiguous candidates before mounting, and leaves other image volumes unmounted. A separate bounded metadata-only discovery operation reports scoped container/volume UUIDs, names/roles and qualified group inventory; it never unlocks APFS volumes, mounts a filesystem or traverses file content. Discovery has the same full source-preservation/owned-cleanup contract. Metadata declaration is separate from positive plaintext support and boot acquisition.

The parent owns the unique scratch directory and attached image. Commands have a fixed executable allowlist, sanitized environment, bounded output, monotonic timeout, cancel token, private process group and owned-child reap. Cleanup detaches only devices discovered for that unique private image. If detach cannot be confirmed, the adapter fails and retains the backing copy; it does not delete a still-mounted backing file or eject another image/device. Cleanup failure is not counted as successful cancellation.

## Credentials and encryption layers

Credentials are supplied by an explicit caller as a single-use memory value. Disk-image credentials are NUL-terminated stdin bytes as documented for `hdiutil -stdinpass`. They are excluded from argv, environment, Codable models, logs, raw error capture, case manifests and reports. Clearing owned buffers is best effort; Swift, system components and the filesystem driver can hold copies. No keychain write or retrieval is performed by application code.

Positive encrypted-UDIF tests prove a container-encryption combination only. They do not prove encrypted APFS-volume or boot FileVault support. The separate disposable-image Disk crypto user profile has an independently measured positive plaintext oracle and a production API with its own `volumePassphrase` stdin transport, idle crypto-migration check, successful crypto-user UUID binding, and fresh unlocked-state check. Its production integration tests remain separate from the OS fixture. Recovery-key/users, hardware-bound system keys, boot acquisition, locked snapshots and privilege requirements remain separate gates. Unknown encryption states and unsupported users are refused. Raw ciphertext scanning cannot become a plaintext result.

[Apple's FileVault security description](https://support.apple.com/guide/security/volume-encryption-with-filevault-sec4c6dc1b6e/web), published 28 January 2026, distinguishes internal Apple Silicon/T2 storage with Secure Enclave and hardware-UID key protection from removable-storage encryption. Consequently, a synthetic Disk-user encrypted volume, a VM guest's encryption and hardware-bound boot acquisition are separate profiles. Labelling synthetic volumes System/Data does not demonstrate a boot FileVault acquisition or access to hardware-bound keys.

## Snapshot policy

Snapshot inventory may be read through `diskutil apfs listSnapshots -plist` for the owned mounted device, and UUID/name/transaction identifiers are retained as inventory. Inventory is not a mounted snapshot view. Apple's [snapshot system-call manual](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/fs_snapshot_create.2) documents privilege and entitlement restrictions; the [current XNU dispatcher](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/vfs/vfs_syscalls.c#L14342-L14433) first requires accepted snapshot entitlements, then permits some device-authorized non-root callers. Image ownership alone does not bypass that first restriction. This project will not request host root, manufacture private entitlements, alter host snapshots or run global host `tmutil` commands to manufacture a positive fixture.

The installed `mount_apfs(8)` separately documents `mount_apfs -s NAME BASE_MOUNT OWNED_DIRECTORY`, where the base argument is the already-mounted volume root. An isolated no-root experiment mounted an owned image's existing snapshot through this ordinary mount route. It bound the public FD volume UUID to the native snapshot UUID/name/XID, retained the base volume identity, verified `MNT_SNAPSHOT` plus read-only/no-exec/no-suid/no-device flags and distinct filesystem IDs, and remounted after acquisition freeze to read exact earlier bytes while the current view read different later bytes. The subsequent production plaintext-UDIF gate passed current/historical inspection, fresh byte verification, immutable case generations/reopen, context-forgery/unknown-selection rejection, export and cooperative cancellation. Those runtime observations remain separate from GUI/distribution and other encrypted/acquisition profiles. No private entitlement, host snapshot change or hardware FileVault capability follows from this result.

The actual integration initially exposed a Foundation alias issue: URL conversion produced `/tmp` even after `resolvingSymlinksInPath`, so the snapshot command's required `nofollow` option rejected the symbolic ancestor with exit 65. A separately owned native `/tmp` negative reproduced the exact stderr; a canonical `/private/tmp` positive preserved both file-byte oracles and original/private identity/hash. Snapshot source/target/unmount strings now come directly from held directory `F_GETPATH`, with no-follow component, dev/inode/mode/owner/flags/fsid and named-descriptor checks. No mount option or ownership/source guard was relaxed. Four SDK canonical-path regressions and the full actual historical oracle passed in the 34-test gate.

Bounded research found no downloadable image with a qualified historical byte oracle. The isolated alternative pinned the MIT [go-apfs-v2 writer](https://github.com/deploymenttheory/go-apfs-v2/tree/f9b546ab72f388f26c2fcfd86d0a952f387fdbef), verified exact Git source blobs and dependency checksums, and created a 256 MiB owned image containing known bytes and a snapshot. Apple's ordinary filesystem changed only the live file using a same-inode write. Apple fsck accepted both states; a fresh read-only source-bound mount preserved the snapshot's earlier bytes and the live later bytes. A COW construction copy produced a plaintext UDIF with the same content/identities, without converting or attaching the frozen original. The ignored lab retains source/license/build and separate raw/UDIF receipts. The larger macOS VM factory remains unexecuted and unnecessary for this plaintext oracle; neither route establishes physical Secure Enclave FileVault compatibility.

## Acceptance and remaining scope

Tests must independently create bytes and containers, verify source hashes/identities before and after, compare exact plaintext bytes from a separate system read-only oracle, refuse symlink escape, prove the actual kernel read-only flag, and check owned device cleanup. Wrong/missing credentials and malformed/non-APFS/multiple-volume images must fail safely. Raw, unencrypted UDIF and encrypted UDIF are separate positive cells. APFS volume encryption, boot FileVault, snapshot inventory versus snapshot content, old OS and physical M5 cells remain separately named. See [the matrix](APFS-COMBINATION-MATRIX.md) and [fixture receipt](APFS-FIXTURE-RECEIPT.md).

The system driver is a trusted OS parser and is outside the document-decoder XPC sandbox. Attaching a user image is an explicit local system operation; an isolated document parser does not isolate the kernel filesystem driver. The adapter is experimental until runtime and cancellation receipts meet this contract. Its performance is measured independently from TSK so private-copy/hash/mount costs are not hidden in a misleading engine-speed comparison.
