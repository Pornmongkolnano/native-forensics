# Case content query modes

Content Search selects Literal, Phrase or Token prefix explicitly. Query text is not SQL, FTS5, a regular expression or an operator language. Changing modes preserves the raw input. The default and the existing Core `search(String, in:, caseSensitive:, maximumHits:)` API remain literal substring searches, including punctuation, Thai without spaces, one/two-character input and combining marks.

| Mode | Meaning | Example in `cat,\ncat scatter catfish` |
|---|---|---|
| Literal | Find the entire raw substring, including punctuation and spacing | `cat` matches both complete `cat` words, the middle of `scatter`, and the start of `catfish` |
| Phrase | Find an ordered adjacent sequence of complete word tokens; Thai-only queries additionally omit internal whitespace while anchoring both ends to real token boundaries | `cat cat` matches `cat,\ncat`; `ภาษา ไทย` and `ภาษาไทย` both match the complete Thai compound or its spaced form |
| Token prefix | Find the exact raw prefix at the start of one recognized word token | `cat` matches complete `cat` words and the beginning of `catfish`, while excluding `scatter` |

Phrase accepts word tokens with whitespace or no gap between them, including no-space Thai. For general word phrases, query whitespace does not constrain decoded-text separators. Punctuation contained inside a recognized word is retained literally. Any other query punctuation is rejected with an explicit message instead of silently removed; use Literal for exact quotes, brackets, wildcard-looking `*`, punctuation or a standalone combining mark. Token prefix requires exactly one raw word token covering the whole query, without surrounding spaces or a trailing `*`. `AND`, `OR` and `NOT` have ordinary word meaning; quotes and asterisks never select a mode.

A phrase stays inside one decoded reference/page. General word phrases can include spaces, punctuation or line breaks between adjacent words. Overlapping phrase matches count separately. Literal retains the existing nonoverlapping substring iteration. Prefix hit length covers the matched prefix, rather than the entire word. Phrase hit length covers the original span from the first word's start through the last word's end, including all intervening text.

When every query token contains only Thai letters or Thai combining marks, Phrase concatenates those exact raw token contents and compares them across consecutive existing Thai word tokens. Only Unicode `White_Space` between those source tokens is omitted from comparison; the query validator uses the same scalar property for omitted query gaps. Tabs, line breaks, nonbreaking spaces and Unicode spaces are accepted. Zero-width space U+200B, BOM U+FEFF and word joiner U+2060 are format characters and are never discarded as whitespace; Literal can search them exactly. Both match edges must remain existing token edges: `ภาษา ไทย` can match the whole `ภาษาไทย` compound without asserting a dictionary split into `ภาษา` and `ไทย`. It cannot match interior `ษาไทย`, cross `ภาษา-ไทย` or an intervening Latin token, or merge Latin `cat fish` into `catfish`. Thai digits, punctuation and mixed-script queries use the general word-phrase rules. Token prefix always retains actual token starts and the single-token requirement; it does not inherit this phrase comparison. [Swift scalar whitespace property](https://developer.apple.com/documentation/swift/unicode/scalar/properties-swift.struct/iswhitespace)

## Unicode and word boundaries

Word modes start with Foundation `NSString.enumerateSubstrings` using `.byWords` and `.substringNotRequired`, without `.localized`. Thai-bearing word spans are refined by a local `NLTokenizer(unit: .word)` with `.setLanguage(.thai)`. Its token ranges are converted against the original span and translated into the original page's UTF-16 range. Non-Thai spans retain Foundation boundaries. If refinement yields no tokens, the original existing word span is retained; character tokens are never invented. [Apple tokenizer and thread ownership](https://developer.apple.com/documentation/naturallanguage/nltokenizer), [explicit language selection](https://developer.apple.com/documentation/naturallanguage/nltokenizer/setlanguage(_:))

Both token layers retain decoded text and raw query bytes without normalization. The query validator explicitly checks omitted query ranges. General matching uses `NSString` literal comparisons with optional case insensitivity and does not fold diacritics. Thai-only phrase comparison uses unchanged Thai UTF-16 units; Thai letters have no case distinction. Query request equality compares raw UTF-8 bytes, so composed `café` and decomposed `cafe` + U+0301 remain distinct reference bindings. A no-space Thai query can contain one compound token or several recognized tokens. Token prefix accepts it only when it is exactly one raw token; Literal still searches the entire exact input. [Apple string enumeration and searching](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPInternational/InternationalizingYourCode/InternationalizingYourCode.html)

The UI shows the actual query word tokens. Word boundaries can depend on the platform's tokenizer and text context. Explicit Thai language selection does not certify linguistic meaning, dictionary completeness or behavior across every macOS version. Unicode notes that dependable word boundaries for Thai and several other languages require dictionary lookup or other tailoring. The small no-space Thai fixture asserts expected sample ranges independently; it is not a general Thai coverage claim. Literal remains available when the desired text crosses an unexpected word boundary. [Unicode word-boundary guidance](https://www.unicode.org/reports/tr29/#Word_Boundaries)

The [synthetic API receipt](benchmarks/phase2-thai-tokenizer-api.json) records an interpreted JXA experiment on macOS 27.0.1: `NLTokenizer(.word)` with explicit Thai and `CFStringTokenizer` with an explicit `th_TH` locale both retain `ภาษาไทย` as one `(0,7)` token. The spaced form exposes `(0,4)` and `(5,3)`. CF word-boundary mode gives the same compound boundary, so switching APIs did not supply the initially assumed component split. The tests keep their original independent matched ranges, but correct the new query-token/prefix assertions to the observed one-compound contract. The experiment is not a repository build/test receipt. Apple documents locale-aware CF word-boundary mode separately from word mode. [Apple CF word-boundary option](https://developer.apple.com/documentation/corefoundation/kcfstringtokenizerunitwordboundary)

All offsets and lengths are UTF-16 positions in the unchanged saved decoder output. They are not source-image or document byte offsets. Emoji, surrogate pairs and decomposed marks retain their original positions; excerpts avoid cutting a surrogate pair. Excerpts are capped at about 160 UTF-16 units even if a phrase spans a very long separator. A full reference can span more text than its excerpt.

## Query binding, work and limits

The mode-aware API returns `CaseContentQueryOutcome`, retaining `ContentIndexQueryRequest`, raw query tokens, a validation issue when applicable, and immutable `ContentIndexQueryReference` values. Each query reference wraps the existing generation/listing/locator/container/content/derived-text/decoder/page/range binding and adds case ID, raw query, mode and sensitivity. Current provenanced documents additionally bind the complete decoder receipt digest and verify that the generation's full worker/broker/backend/contract/options identity matches the receipt. Historical nil/nil references keep their legacy behavior; a missing proof on a current generation cannot be downgraded to that mode. `resolve(queryReference, in:, expectedRequest:)` checks those bindings and re-matches the exact range under that request. Changing its query, mode, case, source binding, receipt/header identity or span cannot resolve as an unrelated context. The optional expected request is compared byte-for-byte. Recorded-file navigation still uses the existing underlying `ContentIndexReference` callback.

General phrase matching streams word ranges through a KMP matcher with only query-sized state and a query-sized ring of ranges. Thai-only phrases use streaming KMP over exact Thai units, with a query-sized ring of original positions and token-start flags; no page-sized compact copy or token array is created. Non-Thai words and non-whitespace gaps reset that comparison. Prefix streams words and anchors a literal match at each word start. Query size remains 4,096 UTF-8 bytes. All modes return at most 200 hits; finding an additional hit sets the explicit limit flag, while exactly reaching the limit does not. Search checks cancellation while visiting files, pages, matches, words and Thai units and stops enumeration before throwing. These are bounded application algorithms, not an Instruments RSS or latency measurement.

Invalid phrase/prefix input displays a validation message, rather than an ordinary zero-match result. The UI owns mode and sensitivity as part of its search generation and cancels superseded work before publishing results. The reference sheet validates a bound query in a detached, cancellable task, retaining its result for the same generation/reference instead of tokenizing during each render. Recorded-file navigation performs the existing source-bound metadata check. Reopen/historical/stale and partial-coverage semantics remain as described in [Content index provenance](CONTENT-INDEX.md); a negative result never proves absence in skipped, failed, pending, unlisted or undecoded content.

## SQLite decision and validation

The earlier [substring/trigram experiment](CONTENT-INDEX.md#substring-versus-fts5-experiment) remains a semantics experiment. FTS5 provides phrase and prefix operators, but it tokenizes input and trigram full-text queries do not match substrings shorter than three Unicode characters. Those characteristics cannot preserve every literal query by themselves. This implementation adds explicit phrase/prefix behavior over the existing bounded generation and never passes user query text to SQL or a MATCH parser. SQLite acceleration remains a separate future decision requiring parity of raw literal results and exact references. [SQLite FTS5 phrases, prefixes and trigram limits](https://www.sqlite.org/fts5.html)

`ContentIndexQueryTests` uses fixed expected offsets for whole words versus middle-of-word substrings, prefix starts, punctuation/newline adjacency, repeated-token fallback, overlap, page separation, composed/decomposed text, the no-space Thai sample, Thai whitespace/compound comparison, punctuation and mixed-script rejection, Thai marks, raw syntax validation, query/reference forgery, extra-hit limits, long separators and cancellation. `ContentIndexWorkspaceTests` additionally covers mode/sensitivity replacement and close races. The existing literal tests remain intact. Test source is not a test receipt: current build/test outcomes and actual-helper/GUI validation must be recorded separately by the normal repository gates.
