# APFS combination matrix

The APFS adapter is a separate experimental system-mounted **allocated view of regular-file main data forks**. It does not enumerate xattrs/resource forks/alternate streams as file content. Each cell requires its own independent content oracle and source-preservation receipt. TSK format support, successful rejection of encrypted input, empty snapshot inventory, and encrypted UDIF success do not establish APFS/FileVault parity. See [the decision record](ADR-APFS-SYSTEM-VIEW.md) and [independent fixture method](APFS-FIXTURE-RECEIPT.md).

## Read contract

Source receipts cover the selected container's complete stored bytes. The adapter creates a private copy-on-write clone from a pinned read-only descriptor, or a streaming private copy. Original and private bytes each receive full hash verification before and after the read; original identity must remain unchanged. The original is never attached. `-noverify` suppresses the DiskImages checksum-xattr cache observed on encrypted UDRO files; it does not replace the adapter's independent complete SHA-256 checks.

The private image is attached read-only with automatic checking/mounting disabled. The nil UUID default requires exactly one identified APFS volume. An image with several volumes requires an explicit UUID matching exactly one candidate; duplicate, absent or ambiguous identities fail before mounting. An encrypted APFS volume must have a recognized, completed encryption state and the supported Disk crypto user; credentials are sent through stdin only, and unlock success/UUID/locked-state are checked. The adapter explicitly mounts only that volume with read-only, no-exec, no-suid and no-device flags and checks those flags through the actual kernel mount descriptor. Other image volumes must remain unmounted. Traversal refuses links and nested filesystems.

`discoverVolumes` performs a separate bounded metadata-only operation: it attaches only the read-only private copy, verifies actual readonly-media declarations and scoped container/volume UUIDs, and never unlocks APFS volumes, mounts a filesystem or reads file content. Its catalog keeps names/roles and source/container/volume identities, omits device/host paths, and qualifies volume-group absence only when scoped inventory was actually available. It independently verifies original/private full source bytes and identities and detaches before returning. Catalog metadata remains distinct from plaintext support and an allocated-file inspection.

The optional snapshot selection resolves only a fresh owned-volume inventory UUID. The validated plain UDIF and AES-256 encrypted UDIF content routes require an unencrypted APFS volume, retain its base volume UUID and mount the resolved name into a second private view. They require the public FD volume UUID equal the selected snapshot UUID, actual `MNT_SNAPSHOT` and read-only/no-exec/no-suid/no-device flags, the exact snapshot-name/owned-device source, and a filesystem ID distinct from the base. The result and export receipt carry the exact UUID/name/XID tuple. Legacy absent/nil selections remain current views. The production plaintext snapshot/canonical-path gate passed 34 tests in seven suites on 8 October 2026; the separate two-test encrypted-wrapper API gate then passed. An independent OS receipt alone still does not establish another production profile.

Snapshot source/target/unmount commands use raw canonical POSIX strings obtained through the public SDK `F_GETPATH`, with held/reopened directory identity and filesystem-ID checks plus a no-follow component walk. Foundation's `URL.path` can reintroduce `/tmp` for `/private/tmp`; an actual command with that alias failed with exit 65 and `Too many levels of symbolic links` under the required `nofollow` mount option. The exact native canonical-path counterpart and repaired production historical oracle passed without removing that option or changing source bytes. Command paths remain transient; the public reader does not retain command stderr.

Default limits are 50,000 aggregate examined names/results, 64 MiB charged metadata, 128 directory levels, 128 MiB per hashed/read file, 4 GiB aggregate logical regular-file hashing, a 64 GiB selected container, 60 seconds per system command and 600 seconds per complete job. Callers can lower them but cannot silently raise them. Row/name/depth/metadata/file-byte limits mark partial allocated coverage; skipped hashes do not become complete content results. These are contract limits, not measured peak-RAM claims or guarantees of complete arbitrary-media recovery. Source verification reads are distinct from logical file hashing.

Every verified file read reopens a fresh source-bound private image. It checks selected-container digest, volume UUID, relative path, regular-file metadata and full plaintext digest against the recorded result. Inode and mtime do not substitute for complete bytes. A stale source or forged/escaping locator cannot produce verified plaintext. All source image paths and mount/device paths remain transient; credentials are not Codable, printed or retained in the result/report model.

Successful jobs detach the uniquely owned image and remove only their known private leaves. Cancellation is not reported complete before child reap and mount cleanup. An unknown detach outcome fails and retains the private backing file. Cleanup never falls back to guessed historical disk numbers, source repair, arbitrary recursive deletion, another device's eject or a writable remount.

Normal attach/base-mount/snapshot-mount cancellation lets an already-started read-only utility reach natural terminal within the unchanged command deadline, then unmounts the owned snapshot before base/image detach and cleanup; no file hashing, preview or extraction continues after that cancel. Hard workflow/command deadlines and output bounds remain enforced. A client killed, timed out or stopped for output bounds may leave work pending in a separate system component. Reaping that client plus observing an empty instantaneous image list does not prove completion. Such jobs report `cleanupIncomplete`, retain their private backing/mount directory, and write a bounded `quarantine.json` with `cleanupUncertain`; prior result/export publication remains intact. The application never kills a global daemon or declares this state cancelled-clean. Natural terminal command failures, including wrong credentials, still use fresh owned-image inventory/detach cleanup. Gate12's attach cancellation oracles and the later actual snapshot-start cancellation gate passed separately; a cancellation receipt does not itself prove the mount succeeded. Deliberate hard-failure test quarantine is retained for review; it is not a successful scratch-cleanup receipt.

## Honest release boundary

OS fixture success is separate from production adapter success, GUI integration, distribution/old-OS/M5 validation and release trust. The opt-in fixture tests compare the production APIs with independent synthetic bytes and a separate read-only OS mount. The fresh AES snapshot suite uses `NF_APFS_ENCRYPTED_SNAPSHOT_INTEGRATION=1` and the pinned public fixture path; generated keys remain in that process's memory and private stdin, never environment values or saved artifacts. Its initial acceptance runs alone because the public-export default-job cleanup fence rejects concurrent namespace changes. Only a completed test/runtime receipt can move a matrix cell to passed. This matrix does not close encrypted-volume snapshot-content, arbitrary FileVault or other multiple-volume requirements by declaring them unsupported. A passing raw single-volume profile does not establish all raw acquisition layouts.

## Historical storage and export

`APFSResultStore` publishes immutable `apfs/<evidence-id>/generations/<generation-id>/{result.json,checksum.json}` with a separately replaced `latest.json`. The result records complete read options, source-byte hash scope, system component label/version, volume identity, distinct encryption layers, warnings and partial coverage. Reopen validates pointer/result checksums and case/source binding without opening the original image; that metadata is historical. Checksums detect changed bytes and do not authenticate an examiner. The `jobProvenance` helper supplies an immutable artifact path/digest for an explicitly migrated schema-2 case; it does not migrate a case silently.

`APFSExportService` requires the result equal its stored generation, performs a fresh source-bound mount/read, independently rereads the staged output, and verifies the complete original source again immediately before an exclusive new-file publication. It holds the case read lock and refuses existing destinations, sources, case-package paths and directory symlinks. The export receipt distinguishes selected-container and logical-APFS-file hash scopes and omits the destination host path. An uncertain post-rename flush reports a published-but-unconfirmed outcome and retains the committed bytes.

The actual APFS host changes an output's ctime during this owned rename. The exporter adopts only that successful output transition, requires unchanged device/inode/size/mtime, independently rereads complete output SHA-256, and checks held-descriptor/destination identity plus the anchored parent after the directory flush and final read. Original source identity checks remain exact. Gate12 passed the six deterministic rename, mutation, flush-failure, destination-collision, precommit-cancel and postverification-parent-replacement regressions, together with all seven live APFS fixture/cancellation cases.
