# APFS independent fixture receipt

This receipt covers only newly created synthetic image files. The fixture oracle writes known bytes before the application sees them, retains the expected byte count and SHA-256, and later compares those bytes with the application's exported content. Image-container hashes cover the complete stored image, including encryption metadata; they do not claim to be a hash of the decrypted filesystem.

## Exact combinations and current evidence

| Combination | Independent construction route | Local prerequisites | Evidence status |
| --- | --- | --- | --- |
| Plain APFS inside one local UDIF image | Apple `hdiutil create`, APFS, owned synthetic source folder | User-owned output and mount directories | Independent OS oracle and Gate12 production current-view/case/export gate passed |
| RAW logical GPT device bytes containing plain APFS | UDTO construction followed by independent MBR/GPT/NXSB checks and actual attached-device geometry | Verified 512-byte logical sector mapping, GPT CRCs, and full container byte count | Independent OS oracle and Gate12 production current-view gate passed |
| Plain APFS inside an AES-256 encrypted UDIF image | Convert the preceding image to UDRO with `-encryption AES-256 -stdinpass` | Passphrase held only in memory and written to a private stdin pipe | Independent OS oracle and Gate12 production current-view credential/content gate passed |
| An APFS volume whose own crypto state is encrypted with the Disk crypto user | Disposable APFS image, then `diskutil apfs encryptVolume` on its image-derived volume only | Disk ownership, `-stdinpassphrase`, `CryptoMigrationOn=false` | Independent OS oracle and Gate12 production current-view credential/content gate passed |
| AES-256 encrypted UDIF containing an independently Disk-user encrypted APFS volume | Two distinct memory-only credentials and both decryption layers | Separate container and volume credential transports | Independent OS oracle and Gate12 production current-view two-layer gate passed |
| A plaintext APFS historical snapshot inside plaintext UDIF | Owned MIT-writer fixture plus Apple live-only write, then detach/freeze and owned COW UDIF conversion | Ordinary no-root `mount_apfs -s`, canonical descriptor-bound paths, public FD UUID and kernel snapshot/readonly proof | Independent raw/UDIF historical byte oracles and production UDIF inspection/read/reopen/export/cancellation gate passed |
| FileVault on a macOS boot/data volume or hardware-bound Apple Silicon storage | A separately acquired, authorized, independently known image and matching keys | Acquisition profile, exact encryption/key support, positive corpus | Unproven; encrypted UDIF does not establish this combination |

An unavailable snapshot or FileVault fixture is an open gate. A negative result on ciphertext, an empty snapshot list, or a successful encrypted UDIF attach does not close a positive plaintext/snapshot requirement.

## Read-only oracle contract

1. Build only inside a fresh owned temporary directory; durable probe receipts and scripts belong below ignored `local/apfs-combinations`. Place a UTF-8 file containing Thai and combining characters, a deterministic binary payload, and a nested filename containing spaces in the synthetic source folder. Record exact expected bytes before creating any image.
2. Finish all construction writes and detach the construction mount before measuring the image hash. A generated APFS image has randomized filesystem identifiers, so the oracle pins file bytes and each run's final container hash instead of claiming a universal byte-identical image hash.
3. Make a separate private copy whose container hash matches the original, then attach that copy with `-readonly -nobrowse -noautoopen -noautofsck` to a fresh owned mount point. Never use a shadow file, automatic repair, image resizing, encryption mutation, or read-write fallback during analysis. A concrete macOS 27 probe observed DiskImages adding `com.apple.diskimages.recentcksum` to an encrypted UDRO file during a read-only attach: mounted-device read-only flags preserve container bytes but do not imply unchanged source-file metadata. The private-copy boundary keeps this change away from the original evidence.
4. Verify the actual mounted filesystem is APFS and has `MNT_RDONLY`. Record the image-derived device identities. Attempt an owned synthetic marker write and require a read-only failure; the attempt must not create a file.
5. Compare every expected file's bytes and SHA-256 through a separate filesystem read and the production adapter's fresh verified read. Separately exercise an exclusively published export and check its actual bytes plus source/result/output receipt. Verified in-memory content and published output are distinct observations.
6. Detach only devices identified in that attach result, then independently hash the private copy and original image again. Require exact equality of the original size, SHA-256, and source identity before and after analysis, and require the private copy's container bytes to retain the same digest. Record any private-copy metadata changes separately.
7. For an encrypted container, first verify that a missing or wrong in-memory credential produces no plaintext content. Then run the correct credential through stdin and require the same independently known plaintext file bytes as the plain APFS fixture. No credential may occur in argv, environment, command logging, JSON, receipts, reports, or Git.

The fixture must retain cleanup errors rather than treating a still-mounted device as a pass. It must never enumerate, encrypt, unlock, snapshot, or detach host volumes. A symlink inside the image pointing outside the mounted volume is a traversal rejection fixture, not a source of file content.

## Primary documentation inspected

- Local macOS 27 `hdiutil create -help`, `convert -help`, `attach -help`, and the Xcode SDK's `hdiutil(1)` manual. The manual specifies a NUL-terminated passphrase for `-stdinpass`, warns that command-line passphrases are visible in process listings, and documents `-readonly` as forcing a read-only attached device.
- Local `diskutil image create blank --help`, `create from --help`, and `attach --help`. The new image interface documents `--stdinpassphrase`, `--readOnly`, `--noMount`, and owned mount points. It is not assumed available on every advertised older macOS version.
- Local `diskutil apfs encryptVolume` and `unlockVolume` help. These document disk ownership and secure stdin credential input. Documented command availability is not an observed successful unlock.
- Apple's [older XNU snapshot manual](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/man/man2/fs_snapshot_create.2) documents privilege and entitlement restrictions. The [current XNU dispatcher](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/vfs/vfs_syscalls.c#L14342-L14433) requires accepted entitlements before considering device-authorized non-root callers. Snapshot creation or reverting the host filesystem is outside this fixture workflow; the separate owned-guest proposal changes no host snapshots.
- Apple's [APFS overview](https://developer.apple.com/documentation/foundation/about-apple-file-system) describes APFS filesystem features; those features alone do not establish a raw forensic parser's support.

Runtime image hashes, read-only mount checks, individual export receipts, credential failure results, and cleanup results belong in ignored local evidence. The application adapter must also retain its own reconstructible options, component version, source hash scope, selected volume identity, warnings, and any partial-result status.

## Observed fixture probes on macOS 27

The ignored `local/apfs-combinations` receipts distinguish OS fixture construction from production adapter validation. Two independent no-verify/private-copy probes established a plain APFS UDIF and AES-256 encrypted UDIF containing the same plain APFS volume. Each compared three known files, denied a synthetic write with `EROFS`, detached the image, and preserved both original and private-copy full identity and container bytes. `hdiutil isencrypted` identifies the wrapper encryption; `diskutil info` correctly reports `Encryption=false` and `FileVault=false` for the contained plain volume.

A third probe created APFS volume encryption using only its own attached construction image. It waited for `CryptoMigrationOn=false`, detached the construction image, then attached a private copy read-only with `-nomount`. The volume reported `Encryption=true`, `EncryptionThisVolumeProper=true`, `FileVault=true`, and `Locked=true`. A wrong Disk-user credential failed. A correct stdin credential with `diskutil apfs unlockVolume ... -user disk -stdinpassphrase -nomount -plist` returned `Success=true` and `DiskManagementErrorCode=0`; an explicit `diskutil mount readOnly nobrowse -mountOptions noexec,nosuid,nodev -mountPoint ...` exposed the exact known files while retaining read-only flags. Both original and private full identities and hashes remained equal after detaching.

The system's `FileVault=true` label on a disposable encrypted data volume establishes that exact disk-image Disk-user profile. It does not establish macOS boot-volume acquisition, system/data volume groups, recovery users, hardware-bound keys, or decryption of arbitrary acquired FileVault evidence. Snapshot inventory returned an empty `Snapshots` array for these encrypted/current fixtures. Their historical encrypted content combinations remain unvalidated and separate from the later plaintext historical oracle.

The bounded plaintext historical lab pinned MIT `deploymenttheory/go-apfs-v2` commit `f9b546ab72f388f26c2fcfd86d0a952f387fdbef` and verified source Git blobs plus Go module checksums. It created one fresh 256 MiB APFS container with a known 16 KiB file and snapshot. Apple's own filesystem later overwrote only the live inode. After unmount/detach/freeze, a fresh private read-only mount returned BEFORE SHA-256 `712f13ec2ad0f05759975b7b798ec8cdd1166b7f3d51d28ff279c46e487277fd` from the snapshot and different current AFTER digest `f4f68d721a9e07f438bb76269b78769416256ae43cd250fd0dad9d30e8e9c2df`. Apple fsck exited zero with clean output before and after. The public FD UUID equalled native snapshot UUID `3222234B-EE3F-467B-9D1E-D1E430DF8F5B`, name `nf-before`, XID `1`; actual snapshot/readonly flags, source and distinct filesystem IDs were checked. Final original/private raw bytes and full identities remained unchanged, digest `306bdfed059e3fb176bc9f2d9d1788774569bb450721dccc18bbe31669494558`.

Only an exclusive COW construction clone was converted to plaintext UDIF. Its independently verified frozen wrapper is 392,537 selected bytes with SHA-256 `11ddb1a8aa08625a21ba923efdf3cc8c1c11928db0d936d3d009a14651c502b6`; these stored bytes are distinct from the logical raw digest. Fresh automatically detected UDIF mounts repeated both exact file-byte oracles, public snapshot UUID, native tuple and kernel checks. Normal owned snapshot/base unmount and image detach were confirmed, with original raw/private files and prior receipt unchanged. These ignored local OS receipts are fixture evidence, separate from the subsequent production Core pass and remaining GUI/distribution evidence. No VM, root privilege, private entitlement, host snapshot change or hardware-bound key was used.

On 8 October 2026, the production canonical-path gate passed 34 tests in seven suites. `APFSSnapshotFixtureOracle` compared current AFTER and historical BEFORE inspection plus fresh verified reads, saved/reopened both immutable case generations, retained the earlier current generation, rejected unknown and forged snapshot contexts, and exclusively exported the exact earlier 16 KiB with the source/result/base-volume/selected-snapshot receipt. The mounted observer independently checked the private-copy hash/identity, exact owned device and base UUID, native snapshot tuple, FD snapshot UUID, readonly/snapshot flags, distinct fsids and both known byte oracles. Original source full identity/SHA remained unchanged after every operation and final image inspection. Cooperative snapshot-start cancellation passed separately and confirmed normal owned cleanup without producing a result.

The first actual snapshot command exposed `/tmp` aliases introduced by Foundation URL path conversion. The retained failed command had natural raw wait status `16640` (exit 65), empty stdout and 75 stderr bytes with SHA-256 `e28b89bc5058fdaf671e2dda34aaeddcc308ee294350105abaa079df24af556b`: `Too many levels of symbolic links`. A fresh private native `/tmp` negative reproduced those exact facts and preserved source/private full identity/hash; a sequential canonical `/private/tmp` counterpart passed both byte oracles and normal cleanup. The production fix derives raw command strings from held owned-directory `F_GETPATH` with independent named identity/fsid and no-follow component checks. Actual command arguments are re-bound to their FDs in the live fixture. `nofollow`, all existing mount/source/ownership guards and the nil/current result contract remain unchanged. The internal fixture-only stderr hook is absent from public/default reads.

A fourth independent OS probe wrapped the Disk-user encrypted APFS image in an AES-256 encrypted UDRO container with a different credential. The wrong container credential failed before attachment; after the correct wrapper credential attached the read-only device, the wrong volume credential failed while the volume remained locked. Supplying the correct second credential produced all three exact file byte oracles through an explicit read-only mount. Both original and private image full identities and container hashes remained equal after detaching. This is the combined two-layer Disk-user disk-image profile only. The production opt-in suite contains a matching fourth gate, and its result must be observed separately before this profile is advertised as implemented.

A fifth independent probe used UDTO only as a construction route, then verified the produced file as raw logical device bytes: protective MBR; GPT at byte 512 with separately checked header and partition-table CRCs; backup GPT at the final sector; no `koly` UDIF trailer; an Apple APFS partition with bounded sector extents; and an `NXSB` container whose 4,096-byte block geometry fits that partition. The full data-fork byte count equalled the attached physical device's `TotalSize` at 512-byte logical sectors. Known file bytes, read-only flags, denied writes, and original/private identity and hashes all passed. A suffix or UDTO format label alone would not establish this raw profile. The matching fifth production gate remains separate from this OS observation.

Gate12 on 8 October 2026 passed all seven opt-in production `APFSFixtureOracle` cases: these five exact current-volume profiles, cooperative owned-client-start cancellation and the forced-client/late-attach quarantine profile. The plain profile also saved/reopened a source-bound case result and published the known `alpha.txt` bytes with the expected source/result/output receipt, then refused an existing destination. The six deterministic export transaction tests separately passed actual rename ctime transition, same-size/mtime content mutation, directory-flush failure, staging-time destination collision, cancellation during final validation and postverification parent replacement. The parent's complete Core run reported 575 passing tests. These are API/runtime observations; they do not establish a populated historical snapshot, multi-volume selection, arbitrary boot FileVault, old-OS/M5 or release distribution profile.
